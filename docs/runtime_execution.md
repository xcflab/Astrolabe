# Experimental isolated trajectories

`execution.enabled: true` runs configured repeats in separate Python processes, preserving each repeat's original seed and trajectory loop. `execution.max_active` defaults to 1 and sets an upper bound on active repeats. The admission limit starts at at most two and changes at repeat completions based on host CPU load; no benchmark trajectories are created. A graceful stop stops admission and lets already active repeats finish. Output directories may be assigned in a different order; provenance contains each repeat's seed.

This mode fails closed for unsupported components. Currently it accepts MCMC, dummy evaluators, selected CPU losses, and AF3 daemon only when its adapter declares `BROKER_SHARED_ROOT = True` and `BROKER_ADMITTED_PROBE = True`. Predockers, custom selectors, evaluation hooks, structure starts, per-residue plugins, other mutators/evaluators, and unlisted losses are rejected. The default `execution.enabled: false` retains the legacy path.

Each runtime session owns a private artifact directory and authenticated local broker. The broker retains one model subprocess for an exact identity and identical launch command/environment, serializes initialization and forward calls for a declared device, and never replays a request. The device lease is released after the forward, so trajectory CPU work can overlap it. A failed or uncertain worker fences that device for the rest of the session. The broker accepts one explicitly allocated CUDA-visible GPU per session; it does not coordinate with other sessions, other users, or unrelated programs. On owner exit, the broker stops admission, terminates resident workers, waits for active handlers, and cleans its artifact root. Sudden broker death or an unkillable descendant remains an outcome-unknown boundary, not exact recovery.

The session admits at most `execution.max_resident_models` model workers, defaulting to one; raising this explicitly can exhaust device memory and does not enable concurrent forwards.

`CPUExecutor` maintains GPU-hidden Python subprocesses for its lifetime. Inputs and outputs are JSON, in-flight input bytes and item count are bounded, and each result is limited to `max_pending_bytes / (2 * workers)` so completed results are also bounded. `close()` waits for running work and closes workers. This utility is not yet used by the trajectory scoring and preparation code; those stages remain in trajectory processes.

See the task coordination document `EXECUTION_BROKER_API.md` for adapter details. CPU dummy and mock-device tests demonstrate protocol and scheduling mechanics only; they do not validate GPU numerical equivalence or performance.
